# Fortnite 5.41 — full Ghidra decompilation

This repository intentionally hosts the **public** C-like pseudocode exported by
Ghidra for the original Fortnite 5.41 Win64 shipping client. The source binary
is not committed or uploaded as a file in Git.

## Authenticated original executable

- Retail source: `Fortnite/5.41/FortniteGame/Binaries/Win64/FortniteClient-Win64-Shipping.exe`
- SHA-256: `7a1805869283ffa74df400d9e32dda4a1b6c07ebb0e0a1ce027ee846a18bd108`
- Architecture: AMD64 PE32+, image base `0x140000000`
- Original unwind/function entries after Ghidra deduplication: **291,757**

## Where the permanent dump lives

The generated code and function metadata are committed into the public
[`re/fortnite541-ghidra-full`](https://github.com/lizardpeter/Fortnite-reverse/tree/re/fortnite541-ghidra-full)
branch:

- `decompilation/fortnite541/pdata_index.jsonl.gz` — original function
  entrypoints, end addresses and unwinding information (complete inventory).
- `decompilation/fortnite541/functions/pdata_XXXXXX_YYYYYY.jsonl.gz` —
  full generated C pseudocode, original addresses, function signatures,
  callers/callees counts, and explicit decompiler failures for every entry.
- `decompilation/fortnite541/reports/pdata_XXXXXX_YYYYYY.json` — exported
  function counts and failures for each parallel batch.
- `decompilation/fortnite541/last_batch.json` — first smoke-run summary.

Files are compressed, but all content remains human-readable JSON after
decompression. Function address and original `.pdata` ordinal are durable keys.

## Workers and automatic continuation

Two workflows use the public repository's GitHub-hosted runners:

1. [Single-batch/full-analysis entry point](../../.github/workflows/fortnite541-ghidra-full.yml)
   — authenticated original executable, pinned Ghidra 12.1.4 SHA-256,
   first 12-function smoke test, optional manually selected batch.
2. [Parallel automated completion](../../.github/workflows/fortnite541-ghidra-parallel.yml)
   — up to **16 independent workers**, normally **2,000 original functions
   each per wave**, with source SHA verification on every runner. Each
   wave is committed transactionally to the dump branch, then dispatches
   the next wave until every item from the original unwind index has a
   record. A three-hour scheduled run serves as a recovery mechanism for
   runner failures and interrupted chains.

The batch planner reads the existing original-address-based shards from Git,
so old successes are never lost or needlessly reprocessed. It also prevents
failed or merely started jobs from counting toward verified coverage.

## Verified progress and unresolved-function recovery

The `decompilation/fortnite541/status.json` file on the public dump branch is
regenerated by the wave aggregator after validating **every compressed JSONL
record** against its source report. Its counts distinguish:

- `covered_records`: .pdata ordinals with a permanent record (including failures).
- `actually_decompiled`: ordinals with nonempty original Ghidra C pseudocode.
- `decompiler_failed` and `missing_function`: still-unresolved original routines.
- `unprocessed`: original ordinals which still have no Git record.

`decompilation/fortnite541/unresolved.jsonl.gz` persists each failed/missing
ordinal, original RVA range and reported error as an exact retry work queue.
It is **not** counted toward decompiler completion, even when every .pdata
ordinal eventually has some sort of record. The validation fails fast on
truncated gzip files, unexpected ordinals, duplicate ordinals, absent
source reports, inconsistent report counts, or a record claiming a
successful decompilation without C code.

The independent integrity check can also run through
[fortnite541-ghidra-audit.yml](../../.github/workflows/fortnite541-ghidra-audit.yml).

## Second pass: targeted recovery of original unresolved entries

The **entire** source-authenticated .pdata inventory received a first-pass record.
The first-pass ledger at completion reads: 291,757 inventory entries, 284,392
successfully decompiled, 7,325 missing Ghidra functions, and 40 decompiler
failures. These last 7,365 entries are work, not successes.

`Fortnite541Recover.java` retries exactly those original PE ordinals and RVAs
taken from the audited `unresolved.jsonl.gz` queue; it checks every RVA against
the freshly parsed retail executable's .pdata index before attempting C
decompilation. The first 128-entry source-authenticated probe recovered 115
additional real pseudocode bodies, with eight still missing and five failing.

The [parallel recovery workflow](../../.github/workflows/fortnite541-ghidra-recover.yml)
runs up to 16 workers. On the first main-branch push of the recovery
implementation, it divides the original unresolved queue into bounded shards
of 500 original entries, without repeating any first-pass successes.

- Original successful first-pass shards remain **unchanged** at
  `decompilation/fortnite541/functions/`.
- Second-pass original RVA results live at
  `decompilation/fortnite541/recovery/fast_v1/records/` or
  `recovery/full_v1/records/` with independent source summary reports.
- `recovery_status.json` counts distinct second-pass original functions with
  verified nonempty C pseudocode, alongside effective total completion.
- `recovery_remaining.jsonl.gz` preserves the unresolved original entries
  after deduplicating successful recoveries.
- `audit_ghidra_recovery.py` validates the original entry and address,
  all compressed recovery records, and their independent Ghidra reports before
  publishing the combined recovery ledger.

No guessed function bodies, placeholder C, or originally missing routines are
counted as reconstructed C pseudocode. Full automatic PE analysis is an
optional deeper retry mode, not proof that failed original functions are valid
C++ source.

## Remaining source-function boundary conflicts

After the fast 16-runner retry wave, 6,918 additional functions had real C
pseudocode; the **effective** .pdata result reached 291,310/291,757 (99.84679%).
The remaining 447 consist of 406 missing functions and 41 decompiler failures
as observed in the fast second-pass records.

The source-backed fast retry reports separately recorded 390 cases in which
Ghidra's automatically inferred function body contains another original
`.pdata` entry. This motivates a constrained third-pass `split` mode:

1. Confirm the missing function's original `.pdata` RVA and end against the
   SHA256-verified original PE.
2. If Ghidra assigned that genuine start to an earlier inferred containing
   function, remove the conflicting inferred function **only in the temporary
   Ghidra analysis project**, preserving every previously exported C body.
3. Clear only a decoded instruction that incorrectly crosses the original
   function-entry boundary, then disassemble and create the function at its
   authenticated original start.
4. Export actual C, or a machine-readable missing/decompiler-failed record.
   Never claim source-level reconstruction from a stub or manufactured C.

The first split-mode run is deliberately capped at 64 unresolved original
entries to verify safety and practical recovery rate before scaling. Output
is stored separately in `recovery/split_v1` and combined into the existing
effective ledger only after independent audit.

## Final unresolved function analysis

The verified original `.pdata` pass and source-backed retry stages now contain
**291,691 real Ghidra C pseudocode bodies out of 291,757 original entries**
(**99.977378%**). The remaining **66** are explicitly unresolved in the
permanent recovery ledger: 25 missing-function records and 41 Ghidra
decompiler failures.

A bounded `full_v1` experimental stage analyzes the whole authenticated
retail PE using Ghidra's normal analyzers before retrying the authenticated
original `.pdata` entrypoints. This is substantially more expensive than the
previous fast import. The first test is capped at eight of those 66 original
entries, with a 600-second analysis timeout and independent pseudocode output
audit. Only genuine nonempty C bodies that are RVA verified against the
original executable increase the effective completion percentage.

Remaining entries are **not** replaced with generated stubs, guessed
implementations, or invented function signatures. An original function entry
can remain unresolved due to bad disassembly, overlap, corrupt Ghidra IR,
or other compiler/runtime conditions.

## Native function discovery outside PE unwind metadata

A **separate, strictly candidate-level** inventory is provided by
`Fortnite541LeafDiscovery.java` and its
[original-source workflow](../../.github/workflows/fortnite541-ghidra-extra-functions.yml).

It compares executable native functions recognized by Ghidra with the original
source-authenticated and deduplicated `.pdata` entrypoint set. Additional
Ghidra-discovered functions are classified as either:

- `outside_original_pdata`: executable function entrypoints not represented
  by, or contained within, an original `.pdata` range. These may include
  legitimate x64 leaf functions, thunks and Ghidra analysis false positives.
- `inside_existing_pdata`: Ghidra-defined starts inside an original unwind
  function range, not an additional confirmed original function. These may
  reflect real alternate entries or Ghidra segmentation mistakes.

Each candidate preserves its original RVA, executable section, Ghidra name,
body size, thunk status and whether a decoded entry instruction exists.
`discovery/nonpdata_candidates.jsonl.gz` and
`discovery/nonpdata_report.json` live separately from actual C pseudocode
once verified and committed.

A **candidate is not counted as decompiled** or as a new confirmed native
function merely because Ghidra identified it. The no-analysis workflow is a
fast compile/runtime smoke check; the `main` workflow runs full Ghidra PE
analysis before emitting the discovery report. Resolving and decompiling these
candidates is a distinct verification frontier beyond the complete original
`.pdata` inventory.

## Independently decoded non-.pdata direct call targets

The additional `Fortnite541DirectCalls.java` Ghidra pass walks decoded call
instructions in original executable memory, follows each known **direct**
flow destination, and finds entry points lying **outside every authenticated
original .pdata interval**. For each unique candidate target it exports:

- Original RVA and a real decoded callsite witness
- Count of decoded direct CALL edges to that target
- Whether a decoded instruction exists at the target
- Whether Ghidra independently defined a function or thunk at the target

The gzip evidence is stored separately as
`discovery/nonpdata_direct_calls.jsonl.gz` with an auditable count report.
These are source-backed **candidate** leaf functions or thunks, not
automatically decompiled code or proof of standalone original routines.

The fast `-noanalysis` test completed successfully, but it decoded **zero**
instructions and therefore identified zero call targets. The authoritative
target-identification run on `main` enables normal whole-PE Ghidra
analysis before examining decoded call instructions. This distinction
prevents empty fast-import Ghidra placeholders from being mistaken for
real source code.

## Source-authenticated x64 fallback when Ghidra C fails

For the final original `.pdata` entries where all Ghidra decompilation
strategies failed, `disassemble_original_remaining.py` independently
validates the PE32+ AMD64 executable against its pinned SHA256, reconstructs
the original sorted 291,757-entry unwind index directly from the retail PE,
and verifies each selected original ordinal and RVA/end RVA.

It retains each source interval's SHA256, original source unwind address,
actual Capstone x86-64 linear disassembly prefix, source instruction bytes,
and an explicit count/hash of still-undecoded trailing bytes. Linear
decoding is **not** a verified control-flow graph and must not be labeled
original C++ or 100% successful source reconstruction.

The [real GitHub runner](../../.github/workflows/fortnite541-original-x64-fallback.yml)
completed source authentication and cross-checks for all 56 previously
unresolved functions: **7,641 source bytes**, of which **1,234** were
linearly decoded into **469** instruction records; 52 spans have undecoded
tails. This is a concrete original machine-code fallback for later
instruction-level reconstruction, not additional successful Ghidra C bodies.
The `remaining_original_x64` folder in the permanent public data branch
contains this evidence after main-branch validation.

## What “complete” means

- **Inventory complete:** Every unique `.pdata` function-boundary entry
  gets exactly one indexed record, with status `decompiled`,
  `decompiler_failed`, or `missing_function`.
- **Decompiler completion:** Only records with `status=decompiled` actually
  contain generated C pseudocode. Report the status counts; do not relabel
  failures as successful.
- **Not necessarily all executable routines:** Functions without a `.pdata`
  entry (e.g., some leaf functions and thunks) are a further recovery frontier.
- **Not fully reconstructed original C++:** Decompiled C is approximate and
  not equivalent to a compiling, linked, behaviorally verified original
  game project. Recovering class layouts, object lifetimes and exact
  shader/material bindings is subsequent reverse-engineering work.

This public dump is intended to accelerate the Fortnite 5.41
`FMaterialShaderMap`, `FShaderResource`, D3D11 resource-binding,
uniform-expression and UE4.21 material serialization reconstruction.
